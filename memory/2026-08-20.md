# 2026-08-20 — the instrument audited itself

`hay` 0.5.0. **No ranking code changed.** The entire release is the measurement harness, reviewed
as if presenting it to people who do this professionally, and the honest consequences of that.

## The one that mattered most, and moved nothing

The A/B was not feeding both retrievers the same files. `measure-mrr.ts` gave ripgrep `--hidden`
— added back in instrument error 6, because skipping hidden directories hid `.scratch/` — and never
gave `hay` the matching flag. Four versions of headline numbers were produced by running a
retriever that searched hidden directories against one that did not, in a file whose own comment
says the two must be fed identically or the comparison is not one.

Reproduced in thirty seconds rather than argued about: put a definition in a hidden directory,
`rg --hidden` returns it, `hay` returns nothing.

Then the interesting part. Fixed and re-run: **+0.1318 [0.1065, 0.1585]** against the published
+0.131 [0.105, 0.158]. It made no difference. That is not a reason it was fine — it is the reason
the rule is now invariant 6. "It turned out not to matter" is a sentence you are only entitled to
write *after* you have measured it, and I could not have known which way it would go. It could as
easily have been the third time this project retracted a number.

I checked the rest of the flag list the same way and every other filter already had an exact
counterpart inside `hay`: `--no-ignore-dot` ↔ `.ignore(false)`, `--no-ignore-global` ↔
`.git_global(false)`, `--no-ignore-exclude` ↔ `.git_exclude(false)`, `-g '!.git/'` ↔ the built-in
VCS exclusion. `--hidden` was the only gap *in that file*.

### Then the same bug turned up in the other harness

Having written the rule down as invariant 6, I applied it to `benchmark.ts` rather than assuming
one fix was the end of it — and it was wrong there too, differently. Ripgrep got only
`--no-config`, while `hay` disables the global gitignore, `.git/info/exclude` and `.ignore` files
internally by design, so that operator-local state cannot change results. The ripgrep corpus ships
a `.ignore` containing `!/.github/`, and this machine has `core.excludesFile` set: **231 files
versus 225.** The headline "Δ MRR vs ripgrep" column was partly measuring which files got searched.

I had already killed and restarted the benchmark run once for this. Worth it.

The part that stings: `differential-test.sh` — the script whose entire job is proving `hay` returns
exactly ripgrep's matches — has had the correct symmetric invocation on both sides since it was
written. The right answer was one file away the whole time. The harness that *proves correctness*
was rigorous; the two harnesses that *produce published numbers* were not, and nobody had thought
to compare them. Copy the differential test's invocation; it is the reference.

## What the literature actually says, versus what was cited

Two things came out of reading the sources properly rather than from memory.

**Smucker et al. (CIKM 2007) is cited here to justify a bootstrap.** What the paper does is treat
Fisher's paired randomization test as the *reference* and validate the bootstrap and t-test against
it. Their SIGIR 2009 follow-up then finds the bootstrap systematically biased toward smaller
p-values than the t-test at smaller samples — so the single number this project reported was the
one most likely to flatter it. Citing a paper for the approximation it was used to check is having
the argument both ways. The randomization test now runs at both clustering levels. It agrees:
p=0.0001 by query, 0.0005 clustered by repository.

**MRR was discarding most of the relevance data.** The judgments here are not single-positive — the
mean query has 2.27 answer files, because an agent opens several files after one search — and MRR
looks only at the first. Added nDCG@10 over distinct files: rg 0.373 → hay 0.503, **+0.1306
[0.1097, 0.1524]**. The same effect as MRR, which is the reassuring outcome: the gain is not one
lucky top hit per query. Deliberately *not* added to `benchmark.ts`, where ground truth is one
declaring file per symbol — under single-positive binary relevance nDCG and MRR degenerate into the
same hit-or-miss signal, which is the standing criticism of code-retrieval benchmarks built that
way, and reporting both would be padding.

### The reference test cost a claim on its first run

Worth recording because it is the payoff for the whole exercise. On the public benchmark's openclaw
corpus, `hay` scores +0.150 with a bootstrap interval of [0.005, 0.297] — excluding zero, which is
how the report decided what to bold. The randomization test returns **p=0.058**.

That is the exact failure mode Smucker's follow-up describes, at exactly the sample size it
describes it at (n=30). Under the old rendering that row was bolded as a detected difference. It is
now not, `BENCHMARK.md` bolds only where both tests agree, the disagreement is printed in the
corpus section instead of buried, and `hay`'s benchmark win is reported as detected on **two of
three** usable corpora rather than three.

It still ranks first on all three, ahead of `ast-grep`, which parses the code. But the honest
summary got smaller on the first run of the more rigorous test, which is what a more rigorous test
is for. Anyone can rerun it: `bun benchmark.ts --sample 30 && bun benchmark-report.ts`.

## Review caught a metric bug before it was published

The new nDCG counts distinct **files**; the scan stopped at 1,000 result **lines**. A query whose
first file carried a thousand matching lines would end the scan holding one file and score nDCG 0
with the answer sitting at file-rank 2.

It fired on **0 of 953** queries, so no number was ever affected. The fix stayed in regardless,
because the next corpus is not this one, and truncations are now counted and printed rather than
absorbed into the mean.

The durable lesson is not the cap. It is that `rankOfAnswer` spawns a process, so *nothing about it
was unit-testable* — which is exactly why the bug was invisible. The loop is now a pure
`ResultScan` class with four selftests, including the thousand-noisy-lines case.

Fixing it then introduced a second bug in the same hour: once the scan continues past `RANK_CAP` to
finish the nDCG page, an answer at line 1,201 gets recorded as rank 1,201 and scores RR 0.0008,
where the cap's whole meaning is that it counts as unreachable. Caught by writing the assertion
before trusting the change. That is two defects in one small diff, both in the direction of quietly
inflating the tool's own score.

## Security review

Nothing exploitable, and two things worth writing down.

`hay` has one security property that is genuinely **worse** than ripgrep's, and it follows directly
from what the tool is for. ripgrep orders by path, so content cannot influence its own position.
`hay` orders by content — so anyone who can write a file into a searched tree can choose what an
agent reads first. Write something shaped like a declaration and it outranks the real one. Bounded
(signals are public and `--explain`-able, the match set is still exactly ripgrep's, write access
required), but real, and now in `SECURITY.md` rather than discovered by someone else.

`measure-mrr.ts --json` serialised `RepoScore.path` — the absolute checkout path,
`/Users/<name>/dev/<client>/<project>` — into a payload written next to a committed `evidence/`
directory. Repository identity is what invariant 4 forbids publishing, and serialising the whole
object made publishing it the default rather than a mistake you had to make. Stripped, tested, and
`--json` now warns that the per-repo payload contains real queries. The `--compare` payload was
already aggregates-only; verified rather than assumed.

`cargo audit` ran for the first time ever: clean across 58 dependencies. The private-repository CI
workflow had not executed, so this had not been checked there. `benchmark.ts` and
`benchmark-report.ts` also shipped in 0.4.0 with selftests that nothing ran; both are in CI now.

I also scanned the committed `evidence/` for private identifiers. The suspicious matches were
verified as public benchmark-corpus code; no private identifiers were found.

## The best argument against this tool

From the author of the engine it runs on. BurntSushi, asked for relevance ordering: ripgrep "very
explicitly does not rank results and never will"; if you want ranked results you want an IR system.
In the ngram-indexing RFC he calls it hubris to have thought he could do code-aware relevance
ranking alone, judging it a paid-team problem, and rules ranking out of even an indexed ripgrep.

Both halves are load-bearing and both are now in the README. The first says the gap is permanent
and a wrapper is the right shape. The second is a warning this project has already partly earned —
three of six signals were worth nothing, the definition signal was inert on C for four versions,
and the gate still fails. `hay` is four structural priors and a tie-break, measured; it is not the
thing he said needs a team, and it should not be described as if it were.

## Second session, same day: the error analysis actually happened

Phase 0 (instrument): `--explain` now prints per-signal components from a single `explain_line`
source of truth; `--dump-pairs` writes the per-query paired records `--compare` used to discard;
the pre-registered gate is computed AS WRITTEN for the first time (median across repos — nobody
had ever calculated it; every published number was the paired mean); hay's candidate-cap
truncations are counted during eval; `AST_LANG` no longer silently falls back to Rust. A strict
`tsc --noEmit` gate was added after finding that `pairRepo` checked `a.results === 0` on an
object whose field is `scanned` — the both-invisible exclusion had been dead code since it was
written. Rerun: 952 pairs (one both-invisible query excluded), dMRR +0.1320 [0.1060, 0.1578] —
unchanged. Gate as written: median-repo MRR 0.3870, top-10 0.5816 — FAIL, now honestly.

Phase 1 (taxonomy, issue 10): 466 queries in the miss/regression population. answer-penalized-class
146 (31.3%, mostly prose 78 + test 53), both-lose 145 (all rankable — the "ceiling" framing was
wrong), definition-lang-gap 98 (Swift 106 of the extensions — not Python, not Go), regressions 41,
generic-flood 36, truncated 0, invisible 0. Manual pass (40, `--explain`-assisted) found two
mechanisms: the keyword scan fires on calls (`const body = await readOptionalJsonBody(...)` — the
keyword declares something else) and TS optional properties (`FOO?: string`) missing the `foo:`
rule. Plus one confound worth keeping: several "regressions" are hay putting the true definition
first while the agent opened a usage site — the metric punishes the stated goal.

Fixes shipped in score.rs: word-boundary requirement for the definition signal (mid-identifier
substring matches are never declarations), the `=`/`:` between-keyword-and-match exclusion, and
`foo?:`. Swift corpus (Alamofire) added to benchmark.ts; codespelunker (cs) added to TOOLS — the
"first on all corpora" claim had been made without the closest ranked competitor installed.

Develop-side check on the public benchmark: the precision fixes lifted every corpus measured
before them — linux 0.908→0.949, openclaw 0.836→0.871, ripgrep 0.735→0.800 — and the new Swift
corpus opens at 0.691 vs cs 0.430 / ast-grep 0.444. With codespelunker finally in the field, hay
is first on all five corpora, and the win is now detected on all four usable corpora by BOTH
tests: the openclaw claim the randomization test took away at 0.5.0 came back because the tool
improved, not because the test moved.

Confirmation run (one, per the firewall): dMRR +0.1380 [0.1120, 0.1646], top-10 60.0%. Gate as
written: 0.3810 / 0.5916 — FAIL. Progress without passage; cycle 2 targets the prose/test-answer
bucket, which needs a legitimate development set first.

SWE-Explore-Bench (97 public instances, 8 languages, fixed qderive-v1 rule): dMRR +0.2709
[0.1920, 0.3529], dTop10 +26.8 pts, boot and randomization p both 0.0001. First external
evidence in the project's history. Exclusions counted: 215 pro (no public issue text), 3 no
derivable queries, 0 repo skips.
