## What changed my mind

- **The two axes are independent.** One repo had the cleanest prose share in the sample and the
  worst naming. That killed the composite score idea on evidence, not taste.
- **File-count ratio predicts nothing.** A repo with more prose files than code files scored
  mid-table. Counting documents is the obvious cheap metric and it is worthless.
- **Path class turned out to be `hay`'s strongest signal** (+0.032) even though repo-level prose
  share predicts nothing. A prior can be worthless as a repository score and valuable as a
  per-result tiebreak. That distinction was written down as a hypothesis *before* testing.
- **Three of six ranking signals earned nothing.** Exact-case matching and comment penalties both
  scored +0.000; whole-word scored −0.001 and removing it improved the result.

## Evening — shipping 0.2.0

Closed every engineering item on the "not production-ready" list: `-C/-A/-B`, `--json`,
multi-pattern `-e`, `-t/--type`, `-V`, glued short options, `cargo install`, MIT, and CI across
Linux/macOS/Windows. 27 tests, clippy clean under `-D warnings`, differential test still 10/10.
Median MRR did not move, which is the expected and correct outcome — the gate fails for research
reasons and flags are not research.

Three defects found while doing it, all of the quiet-wrong-answer class:

1. **Truncation was nondeterministic.** Above 20,000 candidates the heap evicted on `prescore`
   alone, so an equal-scoring candidate never displaced the incumbent and the surviving set
   depended on the parallel walker's delivery order. `Ord` on `Candidate` was already total; the
   eviction test simply was not using it.
2. **Empty result hid a hard error.** A search where every path was unreadable exited 1, not 2,
   because the error check sat after the empty-result return.
3. **The A/B fed the two retrievers differently.** `measure-mrr` passed the query to `rg` via
   `-e` but to `hay` as a bare positional, so any query starting with `-` would be parsed as a
   flag by hay and scored unreachable while rg measured it fine — a systematic bias against hay in
   the comparison that produced the +47% headline. Latent, not live: 0 of 2,508 harvested queries
   start with `-`, so no published number is affected. Fixed with the `-e` support added the same
   afternoon.

Also moved the method record out of `.scratch/` into `docs/method/`. `.scratch/` is ignored by
global convention, so every link to it from the README was dead in any clone — and `hay` classifies
`.scratch/` as buried, which is a poor home for the record a reader is pointed at.

## Four review rounds, and the fix that was worse than the bug

Ran `autoreview` (Codex gpt-5.6-sol, P3) to convergence: **5 → 5 → 2 → 0 findings, 12 defects
total**, every one reproduced against ripgrep before and after the fix. Two things worth carrying:

**Two of the twelve were introduced by the previous round's patch.** Round one found that
overlapping `-C` windows printed shared lines twice, once as `-` context and once as a `:` match.
The obvious fix — group overlapping windows into blocks — emitted each block at the rank of its
best member, which dragged a −0.95 result ahead of a 4.85 one. Rank order *is* the product, so the
fix was worse than the bug, and it was also quadratic in the page (~200M comparisons at the
20,000-result cap). The right shape came from the reviewer: keep strict rank order and enforce two
invariants by lookup instead — a shared context line prints once, and a line that is itself a
ranked result is never shown as context. Round three then caught the separator rule in *that*,
because score-ordered windows can run backward.

**The worst two were silent.** `-w` was hand-rolled as `\b...\b`, which cannot match a pattern
whose edges are punctuation — `hay -w -F '@'` returned nothing where ripgrep matches, with exit 1,
indistinguishable from "no matches". And every line went through `str::from_utf8`, so a single
Latin-1 file made hay discard its matches and exit 2. Both were in 0.1.0 and neither was noticed
in a day of using it. `RegexMatcherBuilder::word` existed the whole time.

Lesson, same as always here: hand-rolling something the library already does correctly is how you
get a confident wrong answer. Ask what the dependency already implements before writing the regex.

## The false alarm worth remembering

Re-measuring after the changes moved two repos by 0.0001 MRR. Too small to matter, too large to
have happened at all given the ranking code was untouched. Rather than reason about it: rebuilt the
old binary, diffed its output on exactly the queries that moved — **zero differing lines**. The
cause was 1,795 and 179 files being committed into those repositories *while the measurement ran*.
Two runs of the same binary minutes apart are identical; runs across a day are not. MRR is only
reproducible against a pinned checkout.

## Evening, part two — what expert review would have said

Searched out what the actual authorities in both halves of this project say, and both halves had a
problem.

**IR side.** Fuhr's *Some Common Mistakes In IR Evaluation* (SIGIR Forum 2018) lists ten; this repo
was committing two of them in its own headline. "+47%" is a relative improvement of an arithmetic
mean (his #3) reported with no effect size (his #7) — and computed over twelve repo medians when
the design is paired per query with ~1,000 observations. For a project whose whole finding is *a
metric was published as though validated and was not*, that is the same mistake one level up.
Rebuilt as a paired bootstrap following Smucker et al. (CIKM 2007), who show randomization,
bootstrap and t tests behave alike while Wilcoxon and sign tests should be discontinued:

    MRR    rg 0.2654 -> hay 0.3967   d +0.1312  95% CI [0.1049, 0.1578]
    top10  rg 0.4601 -> hay 0.5830   d +0.1229  95% CI [0.0914, 0.1555]
    by repo cluster: d MRR +0.1312 [0.1018, 0.1574]
    better 574 / worse 225 / tied 153

The effect is real and larger than I could have claimed before. But it also surfaced that **hay is
worse on 24% of individual queries** — "none made worse" was only ever true of repo medians. That
is the more useful sentence and it took the correct analysis to see it.

**ripgrep side.** Rather than guess which flags matter, measured them: 3,174 transcripts, 20,489
search commands. **Combined short flags (`-in`) appear 3,562 times and hay exited 2 on every one**
— four times larger than any other gap. `--smart-case`, which I was about to add on instinct, does
not appear in the top 28. Moved lexing to `lexopt`, the crate ripgrep itself moved to when it left
clap, which supplies combined shorts, `--flag=value`, `--` and attached values at once. That is the
same "delegate to the library" lesson from this morning, applied before the defect instead of
after.

Also added `tests/cli.rs`: nine contract tests against the real binary. There were none — the suite
tested functions and match sets, never what a caller receives.

## 2026-08-20 — the benchmark, and what it caught

Built a public-corpus benchmark against every installed search tool (`ripgrep`, `ugrep`, `ag`,
`ack`, BSD `grep`, `git grep`, `ast-grep`) over the Linux kernel, openclaw, ripgrep's source and
this repo, with ground truth from `ast-grep` rather than from any heuristic under test. Partly a
deliverable, partly the held-out corpus this project has been missing.

**It immediately found the biggest defect so far.** `hay` scored *below* ripgrep on the kernel.
Cause: the definition signal keys on declaration keywords, and C has none — `static int foo(...)`
contains no word from the list. Verified the only way that settles it: on linux, running with the
definition signal switched **off** produced MRR 0.8400, identical to running with it on. For four
versions the tool's entire advantage was absent on the largest C codebase in the world, and no test
saw it because every test was written in Rust or TypeScript.

Lesson worth keeping: **a test suite written in the languages you like cannot find a defect that
only exists in the languages you did not test.** The benchmark was worth building for this alone.

Second lesson from the same fix. The first version of the typed-declaration rule regressed Rust
(−0.017, p=0.0016). Rather than guess, I counted what preceded each false firing across the Rust
corpus: `match` 11, `in` 5, `dyn` 2, rest English prose in comments. Excluding those cut the
regression five-fold to below significance. The counting took ten minutes and the guessing would
have been wrong.

Also confirmed, incidentally: ripgrep's default output order really is nondeterministic. Its MRR
on the same 28 kernel queries came out 0.637 on one run and 0.591 on another, with `--sort path`
stable at 0.671. The project asserted this in the README; the benchmark reproduced it by accident.

Review found four defects in the harness before any number was published — hard-coded Homebrew
paths, a timeout that recorded itself as not-a-timeout, a perf timeout that killed the `time`
wrapper and left the search orphaned holding the pipe, and "peak memory" taken from the first query
only. Fixed before the run that produced the published figures.
