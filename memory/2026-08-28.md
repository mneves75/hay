# 2026-08-28 — v0.3.0: closing the rows that sent readers elsewhere

## The question

> "How can we enhance this tool to be the only one tool for this job (agent search)?"

The README's decision table had eight rows and four of them sent the reader to another tool. The
first thing worth doing was reading what the field currently says, and the field says the goal is
wrong: code search for agents is **three modalities** — lexical, structural, graph — and
"there is no single grep replacement for AI agents". The same source concedes what a unified tool
would have to do: serve all three behind one interface.

That reframed the work usefully. Not "beat the three-modality argument" but **"which of those four
rows were the tool's own fault?"** Three were. One is not, and now says so with a citation instead
of an apology.

## What shipped

**Unranked modes.** `-c`, `--count-matches`, `-v`, `-o` used to exit 2 saying "use `rg`", on the
correct grounds that they leave nothing to rank. That reasoning produced a tool you could only
reach for once you already knew the question ranks — a decision pushed onto the caller before they
could use it. They run now, unranked, in ripgrep's own traversal.

**`--stream`**, pre-registered in DESIGN-hay.md before a line of Rust existed and never built.
Skips ranking, so there is **no candidate cap**: a pattern matching more than 20,000 lines is
answered exhaustively instead of exiting 2.

The interesting part was the ordering choice. I built it sorted first, for determinism, and
measured 8.0 s to the first line of a kernel search against ripgrep's 1.1 s. A drop-in six times
slower than the tool it replaces is not one. Using ripgrep's parallel traversal gives 2.3 s to
first line and 2.50 s against 2.57 s for a complete search — at the cost of being **the only mode
whose order is not deterministic**, which `--help` now says out loud.

## The signal that worked and was deleted anyway

Documentation search is the one row where hay is measurably *worse* than ripgrep. The cause is
structural: prose is charged −1.5 by the path prior and the definition signal never fires there, so
any source file with a declaration-shaped line outranks the document that documents the term.

A markdown heading declares the section about a term as `function foo` declares `foo`. Implemented,
it did not close the gap — it reversed it: −0.010/−0.072/−0.087/−0.194/−0.054 became
**+0.190/+0.109/+0.302/+0.151/+0.454** across the five documentation corpora. Contribution to the
code track: exactly +0.0000, because it is gated on prose extensions and cannot fire on source.

It does not ship. The documentation track's ground truth **is** "this token appears in exactly one
markdown file's headings", so a heading detector is an oracle for the benchmark's construction rule
rather than a retrieval improvement. I wrote that down before taking the numbers, which is the
difference from the v0.2.0 filename deletion — that one was decided after seeing them.

The subtlety worth keeping: the SWE-Explore difference (−0.0054 on n=96) is **not** the reason.
It is not distinguishable from zero, and the harness computes no interval between two hay variants,
so resting the deletion on it would have been its own overclaim. The deletion rests on the
circularity, which is an argument about what the benchmark can know rather than about a number.

## What the review found, which is the real story of the day

Three independent reviewers (correctness, methodology, security), each finding verified against the
built binary before acceptance. **Twenty real defects in two commits, all mine, from that morning.**

The worst: **`hay -o -v` printed nothing and exited 0.** Under `-v` the searcher delivers
non-matching lines, so slicing match spans out of them found none — a search returning nothing while
reporting success, breaking the single promise the tool makes. Eight more of the same family:
`--count-matches -v` reporting 0 for every file, `-o` charging the `-m` budget per substring where
ripgrep caps lines, `-o` discarding context ripgrep prints, `-c` ignoring `-m`, the `--` separator
vanishing when the walk went parallel.

Every one lived in a **pair** of flags. The single-flag differential cases I had written all passed.
Seven combination cases now exist, and that is the transferable lesson: *the cases you write are the
ones you thought of, and defects live where two features meet.*

Security found a formula-generator that read its checksum with `awk '{print $1}'` over every line,
so an appended line in a `.sha256` asset became text interpolated into generated Ruby; an
attestation check scoped to the repository rather than to the workflow and tag; and a tag glob
admitting `v1.0.0"; system("id"); #`.

And the one that stings: the R-precision rationale cited **a withdrawn preprint** for a statistic
that is not in its abstract — lifted from a search summary nobody opened. In the file whose entire
purpose is measuring that class of failure. Open the source.

## Two methodology corrections worth more than the code

1. **R-precision is not independent evidence.** It correlates r=0.905 with reciprocal rank and
   r=0.845 with nDCG@10 on this corpus. It stays, because speaking the field's units is worth
   something, but the correlation is printed beside it — a fourth number that moves with the other
   three reads as fourfold confirmation to anyone who does not check. The near-collinearity is
   itself the finding: here, "wasted reads" and "how far down the answer sits" are one fact.
2. **The measured binary corresponded to no commit.** The heading signal was built, measured and
   deleted inside one session, so the payloads behind a deletion decision came from a tree nobody
   could reconstruct. `evidence/ablations/` now holds them, a README saying what they cannot show,
   and a patch that rebuilds that binary — applied, built and reverse-applied to prove it
   round-trips byte-identically.

## Still true

The gate still fails at **0.4437 / 0.7849** against 0.50 / 0.80. No ranking signal changed in this
release, so it could not have moved, and it did not.
